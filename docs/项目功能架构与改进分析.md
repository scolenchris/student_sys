# 学生成绩管理系统功能、架构与改进分析

分析日期：2026-07-22  
分析范围：`app/` 后端、`src/` 前端、运行配置、数据模型、导入导出、统计与权限链路。

## 1. 项目定位

本项目是一个前后端同仓的学生成绩管理系统，面向学校教务管理和教师成绩录入场景。系统采用 Flask 提供 API 和静态资源托管，Vue 3 + Element Plus 提供前端后台界面，SQLite 作为默认本地数据库，`python run.py` 作为一体化启动入口。

当前系统已经具备较完整的教务闭环：

- 账号注册、登录、审核、强制改密。
- 管理员维护教师、学生、班级、任课、考试任务。
- 教师按任课权限录入、导入、导出成绩。
- 管理员可代录成绩、批量导入成绩。
- 支持综合成绩统计、成绩变化比较、班级成绩统计、教师教学统计、教师端班级级排趋势。
- 支持导入历史记录和部分批次回退。
- 支持成绩修改审计日志。
- 支持学籍证明 Word 文档生成。
- 启动时自动创建表、初始化默认管理员和基础科目。

## 2. 技术架构

### 2.1 后端架构

后端基于 Flask 应用工厂模式：

- 应用入口：`run.py`
- 应用创建：`app/__init__.py`
- 配置：`config.py`
- 数据模型：`app/models.py`
- 认证工具：`app/auth_utils.py`
- 授权校验：`app/license_guard.py`
- 业务路由：
  - `app/routes/auth.py`
  - `app/routes/teacher.py`
  - `app/routes/admin/*.py`
- 服务层：
  - `stats_service.py`：成绩统计与趋势计算。
  - `excel_service.py`：Excel 导入、导出、模板生成。
  - `rollback_service.py`：导入批次回退。
  - `progress_service.py`：成绩录入进度。
  - `audit_service.py`：成绩修改审计。
  - `document_service.py`：学籍证明渲染。

后端接口按角色划分为三个前缀：

- `/api/auth`：登录、注册、修改密码、注册开关查询。
- `/api/admin`：管理员端所有管理、导入导出、统计与审计能力。
- `/api/teacher`：教师端任课、成绩录入、历史查询与趋势分析能力。

### 2.2 前端架构

前端使用 Vue 3 组合式写法，Element Plus 作为主要 UI 框架：

- 入口：`src/main.js`
- 根组件：`src/App.vue`
- 路由：`src/router/index.js`
- API 封装：
  - `src/api/auth.js`
  - `src/api/admin.js`
  - `src/api/teacher.js`
- 管理端页面：`src/views/admin/`
- 教师端页面：`src/views/teacher/`
- 全局主题：`src/styles/theme.css`
- 布局尺寸偏好：`src/composables/useLayoutSize.js`

前端路由通过 `meta.requiresAuth` 和 `meta.role` 做页面级权限控制，接口请求通过 Axios 请求拦截器自动添加 Bearer Token。

### 2.3 数据模型

核心模型包括：

- `User`：系统账号，区分 `admin` 和 `teacher`，支持审核状态与强制改密。
- `Teacher`：教师档案，与账号一对一。
- `ClassInfo`：班级，以 `entry_year` 和 `class_num` 表达入学届与班号。
- `Subject`：科目基础表。
- `ExamTask`：考试任务，包含考试名称、入学届、学年、科目、满分、是否开放录入。
- `Student`：学生档案，包含当前班级、学籍号、身份证号、状态等。
- `Score`：成绩记录，关联学生、科目、考试任务，并通过 `class_id_snapshot` 保存考试时班级快照。
- `CourseAssignment`：任课分配，按教师、班级、科目、学年约束。
- `HeadTeacherAssignment`、`GradeLeaderAssignment`、`SubjectGroupLeaderAssignment`、`PrepGroupLeaderAssignment`：不同类型职务分配，均带学年。
- `ImportBatch`：导入批次，保存范围、摘要、回退快照。
- `AuditLog`：成绩修改审计记录。
- `SystemSetting`：系统设置，目前主要用于注册开关。

## 3. 已实现功能地图

### 3.1 认证与账号

- 登录后签发基于 `itsdangerous.URLSafeTimedSerializer` 的访问令牌。
- 令牌中包含用户 ID、角色和密码哈希签名，修改密码后旧令牌会失效。
- 支持注册申请，注册开关可由管理员控制。
- 管理员可审核或拒绝用户。
- 教师账号审核通过后自动创建教师档案。
- 教师密码可由管理员重置为初始密码，并要求首次登录后修改。

### 3.2 管理员端

管理员菜单分为四类：

- 系统运营：数据可视化大屏、用户审核、系统设置、导入记录与回退、敏感操作审计日志。
- 组织与档案：教师管理、班级管理、学籍管理、任课分配。
- 成绩业务：综合成绩统计、成绩变化比较、手动成绩录入、考试发布管理。
- 教学分析：班级成绩统计、教师教学统计。

管理员主要能力：

- 班级分页查询、创建、删除。
- 学生分页查询、新增、编辑、删除、导入、导出、生成学籍证明。
- 教师分页查询、档案编辑、职务分配、导入、导出、重置密码。
- 任课分配查询、新增、删除、导入、导出。
- 考试任务发布、编辑、锁定/开放、删除，并展示录入进度。
- 管理员按班级和考试任务手工录入成绩。
- 批量生成成绩模板、导入多科成绩。
- 查询导入历史，并按批次回退学生、教师、任课、成绩导入。
- 查询成绩修改审计日志。

### 3.3 教师端

教师菜单包含：

- 成绩录入。
- 班级级排趋势。
- 历史成绩查询。

教师主要能力：

- 查看当前教师已分配且存在开放考试的任教课程。
- 获取首页待办，包括未录入成绩和低分/缺考异常提醒。
- 查看某班某考试的成绩录入名单。
- 保存成绩，支持普通分数和“缺考”。
- 导出成绩录入模板或已有成绩。
- 通过 Excel 导入成绩。
- 查看历史考试和历史成绩。
- 导出历史成绩。
- 查看所任班级在全年级中的排名趋势。

### 3.4 导入、导出与回退

系统已经把较高风险的批量数据操作集中到 `excel_service.py` 与 `rollback_service.py`：

- 学生导入会识别班级、创建缺失班级、更新或新增学生，并保存回退快照。
- 教师导入会处理教师账号、教师档案、级长/科组长/备课组长等分配。
- 任课导入会按学年重建任课与班主任分配。
- 管理员成绩导入采用“先全量校验，致命错误时不写库”的方式。
- 导入记录保存到 `ImportBatch`，回退时基于快照恢复。

这是当前项目中比较成熟的设计，后续建议继续沿用这个思路。

## 4. 关键业务链路

### 4.1 成绩录入链路

1. 管理员发布考试任务，指定入学届、学年、科目、满分、开放状态。
2. 教师通过任课分配获取可录入课程。
3. 教师选择班级、科目后，系统返回对应开放考试。
4. 成绩保存时校验教师是否拥有该学年、班级、科目的任课权限。
5. 成绩写入 `Score`，同时保存 `class_id_snapshot`。
6. 修改已有成绩时写入 `AuditLog`。

### 4.2 统计链路

统计主要围绕 `ExamTask.name`、`entry_year`、`subject_id`、`Score.exam_task_id` 计算：

- 综合成绩统计按考试名称、多科目汇总学生总分和级排/班排。
- 成绩变化比较按多个考试名称比较总分、科目分、级排、班排变化。
- 班级成绩统计计算平均分、优秀率、合格率、低分率、级比率。
- 教师教学统计按任课分配汇总教师所教班级的成绩表现。
- 教师端趋势按班级平均分计算全年级名次变化。

### 4.3 学年、届别与班级快照

项目已经明确把以下字段作为核心约束：

- `academic_year`：学年，用于考试任务、任课、职务分配。
- `entry_year`：入学届，用于班级和考试任务。
- `class_id_snapshot`：成绩归属快照，用于避免学生转班后历史成绩归属变化。

但当前部分统计逻辑仍主要使用学生当前班级 `Student.class_id`，没有完全贯彻 `class_id_snapshot`。这是后续最值得优先修正的业务一致性问题。

## 5. 当前优点

- 前后端边界清晰，页面调用基本都经过 `src/api/*.js` 封装。
- 管理员蓝图已经按账号、学生、教师、任课、考试、导入、统计、审计拆分，维护性好于单一大文件。
- 教师端接口有后端权限校验，不只依赖前端路由。
- 成绩修改令牌会随密码变化失效，安全性比普通静态 token 更好。
- Excel 导入导出能力较完整，覆盖模板、备份、批量录入和统计导出。
- 管理员成绩导入有先校验再写库的设计，能避免部分脏数据。
- 导入批次和回退快照为误导入恢复提供了基础。
- `Score.class_id_snapshot` 是正确的历史成绩设计方向。
- SQLite 启动时会补齐关键索引，有利于本地部署性能。
- 前端已经有分页、关键字筛选、下载、上传、强制改密、布局尺寸切换等较完整的交互。

## 6. 需要改进的问题与风险

### P0：应优先修复

#### 6.1 手工新增任课分配可能直接失败（已修复）

位置：`app/routes/admin/course_mgmt.py`

`CourseAssignment.academic_year` 在模型中是非空字段，但 `add_assignment()` 新增任课分配时没有写入 `academic_year`。同时重复判断也没有按学年判断。这会导致手工新增任课分配时可能触发数据库非空约束错误，或者无法支持同一班级同一科目不同学年由不同教师任教。

修复记录：已在 `add_assignment()` 中读取并校验 `academic_year`，写入 `CourseAssignment.academic_year`，并把重复判断调整为同一学年、同一班级、同一科目只能存在一个任课教师。

建议：

- 前端新增分配表单显式传入学年。
- 后端校验 `teacher_id`、`class_id`、`subject_id`、`academic_year`。
- 重复判断改为四元组：教师、班级、科目、学年，或按业务规则判断同一学年同班同科唯一教师。

#### 6.2 统计逻辑缺少学年过滤，可能混算同名考试（已修复）

位置：`app/services/stats_service.py`

多个统计入口使用 `entry_year + exam_name + subject_ids` 查询考试任务，但没有统一带上 `academic_year`：

- 综合成绩统计。
- 成绩变化比较。
- 班级成绩统计。
- 考试名称查询。

如果不同学年存在相同考试名称，例如“期中考试”，统计可能混入跨学年的考试任务。

修复记录：已将考试名称查询、综合成绩统计、成绩变化比较、班级成绩统计、管理员首页成绩分析、成绩备份模板和管理员严格导入统一补充 `academic_year` 参数，后端按 `academic_year + entry_year + exam_name + subject_id` 定位考试任务。

落实情况：

- 统计页面已统一增加学年筛选。
- 后端统计服务已统一以 `academic_year + entry_year + exam_name + subject_id` 定位考试任务。
- 考试名称接口已支持学年参数，并在前端按学年加载。

#### 6.3 历史成绩统计未全面使用班级快照（已修复）

位置：`app/services/stats_service.py`

系统已经在成绩保存时写入 `class_id_snapshot`，但部分统计仍按 `Student.class_id` 归属学生。学生转班后，历史考试的班级统计、班排名、教师统计可能被当前班级影响。

修复记录：已将综合成绩统计、成绩变化比较、班级成绩统计、教师教学统计中的班级归属口径调整为优先使用 `Score.class_id_snapshot`；旧成绩没有快照时再回退到 `Student.class_id`，兼容历史数据。

落实情况：

- 面向历史考试的核心统计已以 `Score.class_id_snapshot` 优先。
- 没有快照的旧数据会回退到 `Student.class_id`。
- 文档已明确“当前班级”和“考试时班级快照”的区别。

#### 6.4 成绩表缺少唯一约束，重复成绩依赖代码规避（已修复）

位置：`app/models.py`

当前代码多处通过 `Score.query.filter_by(student_id=..., exam_task_id=...).first()` 查找成绩，但模型没有数据库级唯一约束。如果并发保存、重复导入或历史脏数据出现，同一学生同一考试可能有多条成绩。

修复记录：已为 `Score` 模型补充 `student_id + exam_task_id` 唯一约束；SQLite 启动优化阶段会先检测同一学生同一考试的重复成绩，保留 `id` 最大的最新记录，将旧重复行归档到 `score_duplicate_archives` 后删除，再创建唯一索引 `uq_scores_student_exam_task`。教师录入、教师导入、管理员手动录入、管理员严格导入已补充重复写入的中文错误提示。

落实情况：

- 已增加唯一约束：`student_id + exam_task_id`。
- 已提供启动时兼容清理逻辑，重复成绩保留最新记录，旧记录归档。
- 写入侧已补充唯一约束冲突提示；查询侧后续可逐步移除旧的防御性去重代码。

### P1：高价值改进

#### 6.5 数据库迁移能力不足

当前通过 `db.create_all()` 自动建表，但 `create_all()` 不会为已有表补齐新增字段、修改约束或迁移数据。项目已经存在多个关键字段，如 `academic_year`、`class_id_snapshot`、`ImportBatch`、`AuditLog`，后续继续演进会越来越依赖迁移。

建议：

- 引入轻量级迁移机制，优先考虑 Flask-Migrate/Alembic。
- 如果部署环境不便引入 Alembic，至少建立版本化 SQL 迁移脚本和启动前 schema 检查。
- 每次模型变更必须提供旧库升级路径。

#### 6.6 安全配置需要产品化

当前存在以下安全隐患：

- `SECRET_KEY` 有硬编码默认值。
- 默认管理员账号和默认密码固定。
- 教师重置密码固定为 `123456`。
- CORS 对所有来源开放。
- Token 保存在 localStorage，前端缺少统一 401/403 响应处理。
- 注册可申请管理员身份，虽然需要审核，但权限入口仍偏宽。

建议：

- 首次启动强制生成或录入管理员密码。
- 无环境变量时禁止生产启动，或自动生成本机密钥并持久化。
- 重置密码改为随机临时密码或一次性改密链接。
- CORS 限定可信来源。
- Axios 增加响应拦截器，遇到 401 自动清登录态并跳转登录。
- 管理员注册申请可默认关闭或仅允许超级管理员创建。

#### 6.7 审计日志覆盖范围偏窄

当前审计主要覆盖成绩修改，且只有 `adminwds` 可以查看日志。对学生删除、考试删除、导入回退、教师状态调整、管理员审核等敏感操作缺少审计记录。

建议：

- 扩展 `AuditLog.action_type`：`user_approve`、`student_delete`、`exam_delete`、`import_rollback`、`teacher_status_change`、`password_reset`。
- 删除和回退操作记录影响范围。
- 审计查看权限从硬编码用户名改为显式角色或权限字段。

#### 6.8 删除策略偏硬，缺少软删除与二次保护

当前学生删除会同步删除成绩，考试删除会同步删除相关成绩。这类操作风险很高，尤其在教务系统中成绩数据通常需要可追溯。

建议：

- 学生使用状态流转代替物理删除，例如“转出”“休学”“毕业”。
- 考试任务优先使用锁定/归档，不直接删除。
- 如必须删除，要求输入确认短语并记录审计。
- 删除前展示影响范围，例如成绩条数、涉及班级、导入批次。

#### 6.9 导入回退还需要跨类型依赖保护

当前回退只要求先回退更新的同类批次。实际业务中，学生导入后可能又导入了成绩，任课导入后可能发布了考试并录入成绩。只按同类批次判断，仍可能出现跨类型依赖问题。

建议：

- 回退前做影响分析，检查目标对象是否已有后续成绩、任课、考试任务或其他导入依赖。
- 导入批次记录更明确的对象 ID 范围。
- 回退页面展示“可回退原因/不可回退原因”。

#### 6.10 Excel 大文件与统计接口超时风险

前端三个 Axios 实例统一 `timeout: 5000`。导入、导出、复杂统计和大文件下载很容易超过 5 秒，导致前端误报失败。

建议：

- 普通接口保留较短超时。
- 导入、导出、统计接口使用 30 到 120 秒超时。
- 大批量导入改为异步任务，前端轮询进度。

### P2：中期优化

#### 6.11 班级唯一性缺少数据库约束

`ClassInfo` 没有 `entry_year + class_num` 联合唯一约束，新增班级接口也缺少重复校验。重复班级会影响学生归属、任课分配、统计筛选。

建议：

- 增加 `entry_year + class_num` 唯一约束。
- 后端新增班级前做重复校验。
- 导入学生自动创建班级时复用同一标准。

#### 6.12 前后端默认学年口径不完全统一（已修复）

多个页面和后端函数使用“月份 >= 8”或“月份 >= 9”判断默认学年。不同入口默认学年不一致，可能导致教师、任课、考试筛选结果看起来“不见了”。

已完成：

- 前端新增 `src/utils/academicYear.js`，统一默认学年为 9 月切换。
- 后端新增 `app/utils/academic_year.py`，统一接口兜底和模型默认学年。
- 考试发布、教师管理、任课分配、首页看板和成绩统计页面均改为使用统一默认学年工具。
- 保留用户手动选择学年的能力，已有数据库记录不受影响。

后续可选：

- 如学校需要按配置切换开学月份，可再增加系统设置项或 `/system/current_academic_year` 接口。

#### 6.13 错误响应与状态码需要统一

部分导入接口在校验失败时返回 HTTP 200，并通过 `status: error` 表达失败；其他接口返回 400。前端需要记住各接口差异，容易漏处理。

建议：

- 业务校验失败统一返回 400。
- 对“有提示但已成功”的情况返回 200，并明确 `warnings`。
- 前端统一错误提示和日志详情展示。

#### 6.14 查询性能仍有 N+1 和大内存风险

部分统计会一次性加载全年级学生、所有成绩，再在 Python 中计算。数据规模较小时可接受，但随着年级、历史考试和科目增长，响应时间会变长。

建议：

- 统计服务按查询场景增加聚合 SQL。
- 对大报表使用后台任务和分页导出。
- 对高频组合增加复合索引，例如 `exam_task_id + class_id_snapshot`、`student_id + exam_task_id`。
- 对教师端待办按任务和班级批量聚合，减少循环查询。

#### 6.15 前端状态管理较轻，登录态和接口错误分散

当前登录信息主要存储在 localStorage，Pinia 还没有承载用户状态和全局权限。各页面独立处理错误，体验不够统一。

建议：

- 建立 `authStore` 管理 token、role、username、must_change_password。
- Axios 响应拦截器统一处理 401、403、超时和下载错误。
- 页面只处理业务提示，不重复写登录失效逻辑。

#### 6.16 自动化测试缺失

当前仓库没有明显的单元测试、接口测试或端到端测试。成绩统计、导入回退和权限校验都属于高风险逻辑，人工回归成本会持续升高。

建议：

- 后端先补 pytest 测试，覆盖：
  - 登录与权限。
  - 考试发布与锁定。
  - 教师越权录入拦截。
  - 成绩导入先校验后写库。
  - `class_id_snapshot` 统计归属。
  - 导入回退。
- 前端补最小 Playwright 冒烟：
  - 登录。
  - 管理员打开主要页面。
  - 教师查询课程并进入成绩录入。

### P3：体验与工程完善

#### 6.17 使用文档与系统内帮助可继续补齐

仓库已有管理员使用文档，但可进一步补充教师端、导入模板字段说明、统计口径解释、回退注意事项。

建议：

- 增加教师使用手册。
- 在导入页面提供模板字段说明和常见错误说明。
- 在统计页提供“统计口径”折叠说明，明确缺考、缺失、转班、排名并列规则。

#### 6.18 配置与打包路径需要稳定化

`config.py` 使用 `os.getcwd()` 作为数据库路径基础。源码运行、双击 exe、服务方式启动时，工作目录可能不同，导致数据库位置不符合预期。

建议：

- 源码运行时使用项目根目录。
- 打包运行时使用 exe 所在目录或用户数据目录。
- 启动日志明确打印数据库绝对路径。

#### 6.19 依赖与构建产物管理需要整理

`.gitignore` 忽略了 `package-lock.json`，但仓库中存在该文件。生产构建产物 `dist/` 也存在于工作区。需要统一团队约定。

建议：

- 如果是应用项目，建议提交 `package-lock.json`，保证前端依赖可复现。
- `dist/` 保持不入库，发布时由构建流程生成。
- 补充 `requirements.txt` 或 `pyproject.toml`，固定 Python 依赖版本。

## 10. 总结

项目已经具备可用的学生成绩管理主流程，尤其是管理员业务覆盖面、Excel 批量处理、导入回退、教师权限录入和成绩修改审计这些能力比较完整。下一步最应该投入的是“数据一致性”和“长期可维护性”：先修复学年过滤、班级快照统计、任课分配学年、成绩唯一约束这几类会直接影响业务结果的问题，再补安全、审计、迁移和测试底座。
